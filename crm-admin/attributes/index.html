DESCRIPTION

핵심은 「로그가 아니라 집합」입니다. 조작할 때마다 줄을 쌓으면 이름을 세 번 고친 사람의 목록에 A→B, B→C, C→D가 남고, 저장 확인 모달에서 실제로 무엇이 바뀌는지 읽을 수 없습니다. 대상 하나 = 줄 하나가 원칙입니다.

정렬은 발생 순서 · 최신이 맨 아래입니다. 이미 있는 대상을 또 고치면 그 줄이 맨 아래로 내려옵니다 — 방금 만진 것이 항상 눈에 가까이 있게. 상단 스트립은 최근 5줄만 보여주고 위에 「이전 N건」 표시가 붙습니다. 전체는 저장 확인 모달에서 펼칩니다.

구분·속성 타입을 바꿔도 목록은 유지되고 계속 누적됩니다. 저장은 화면 전체가 아니라 변경 대기 목록 전체를 한 번에 반영합니다.

확인 필요 — 서버 저장 API의 페이로드를 이 구조와 맞출지 결정이 필요합니다. 화면이 변경 집합을 들고 있으면 PATCH 성격의 부분 전송이 가능하고, 전체 트리를 통째로 PUT하면 이 목록은 화면 표시용으로만 쓰입니다. 개발자와 정할 부분입니다.

안경로근거 · 문제
㉮ 권장/products/attributes태그가 /products/tags라면 형제로 붙습니다. 이 화면이 다루는 것이 「상품속성」이고 GNB 「상품 관리」 하위이므로 계층이 그대로 드러납니다. 구분·속성 타입은 쿼리로 — ?service=INTERNET&type=SPEED. 그래야 특정 속성 타입을 링크로 공유할 수 있습니다.
㉯/products/tags/attributes진입 경로(태그 관리)를 그대로 URL에 박는 안. 권하지 않습니다 — 이 화면은 태그의 하위 개념이 아니라 태그가 참조하는 상위 사전입니다. 나중에 다른 화면에서 진입하면 경로가 거짓말이 됩니다.
㉰/product-attributes최상위. 「상품 관리」 그룹 밖으로 나가 GNB 하이라이트가 어긋납니다.
DESCRIPTION

㉮ /products/attributes?service=INTERNET&type=SPEED을 권합니다. 쿼리 없이 들어오면 인터넷 · 첫 번째 속성 타입이 기본입니다. 파라미터 이름은 type(속성 타입)입니다 — attribute는 이제 소분류(1Gbps)를 가리키므로 쓰면 안 됩니다.

확인 필요 — 어드민의 기존 상품 화면 실제 경로를 확인해서 맞춰야 합니다. 현재 태그 관리 경로가 /products/tags가 아니라면 ㉮의 전제가 깨집니다. 쿼리값은 한글이 아니라 코드값으로 둡니다 — URL 인코딩과 공유 링크 깨짐을 피하기 위해서입니다. 실제 코드값(INTERNET · SPEED)은 DB 값에 맞춰야 하므로 개발자 확인이 필요합니다.

권장 — 현재창 이동

이 화면의 저장이 상품속성 캐시를 비웁니다. 새창으로 열면 뒤에 남은 태그 관리 창은 옛 속성 목록을 들고 있게 되고, 거기서 태그를 등록하면 없는 속성을 고르거나 바뀐 이름을 못 봅니다. 두 창이 어긋납니다.

현재창으로 이동하면 돌아올 때 태그 관리가 다시 조회되므로 항상 최신입니다. 복귀는 breadcrumb(상품 관리 › 태그 관리)과 툴바의 [태그 관리로] 버튼 둘 다 둡니다.

확인 필요 — 어드민의 다른 화면들이 하위 페이지를 새창으로 여는 관례가 있는지 확인하면 좋겠습니다. 없으면 현재창이 기본입니다.
